# Soundboard Lab: a Blender add-on for luthier soundboard experiments

Working title. Read this first, every session. It frames *what* we're building and the decisions already made, so you don't re-litigate them.

## Purpose

A **domain-specific** tool that lets luthiers run rapid, precise experiments on soundboard acoustic treatments (bracing, contouring, mass loading) as eigenmode analyses, from inside Blender. It is **not** a general-purpose FEA add-on. A small, fixed vocabulary of guitar concepts is what makes the tool both easy to use and verifiable.

Primary user: the author (experimental luthier, "Evergreen" stress-neutralized soundboard system, orthotropic spruce, floating bridge, force compensators). Secondary: the wider luthier community, as an open-source gift. Design for the second without compromising the first.

The author has a full experimental validation stack (tap spectra, Chladni, static-deflection material characterization, laser speckle interferometry in progress). **Correctness is judged against her measurements, not published tables and not by you.** Don't explain acoustics measurement or material characterization to her; implement.

## Stack (decided)

- Blender **5.2 LTS**, extensions system (`blender_manifest.toml`), Windows 11, VS Code.
- **CalculiX 2.22**: `C:\Program Files\FreeCAD 1.1\bin\ccx.exe` (standalone-runnable; no `-v` flag, run bare to see the banner). Path lives in add-on preferences, never hardcoded, never PATH-dependent. **Observed live, twice in one session: these preferences (ccx path + engine venv python path) can lose their values across a routine dev-reload cycle**, even with "Save Preferences" already clicked and Auto-Save Preferences already on -- not user error. Leading theory (unconfirmed): a dev-tooling reinstall of the extension package can reset Blender's own per-addon preferences entry even though the registered `bl_idname` string stays the same. Mitigation built: `analysis.py`'s `_prefs_cache_path()`/`_save_prefs_cache()`/`_load_prefs_cache()` mirror both paths into a plain JSON file under `bpy.utils.user_resource('CONFIG')` (stable, independent of this extension's own install/registration state) every time either field is edited, and a short deferred `bpy.app.timers` one-shot (`_restore_prefs_from_cache_if_empty`, since `context.preferences.addons[__package__]` isn't populated yet at `register()`-call time) restores from that cache automatically if Blender's own preferences come back empty.
- **gmsh + meshio + mesh repair (`pymeshfix` + `trimesh`)** in a normal system **venv**, called by subprocess with explicit full paths. Never import them into Blender's bundled Python (3.13 in 5.2 LTS). `pymeshfix` (Python wrapper around Marco Attene's MeshFix algorithm) does the actual watertight repair; `trimesh` provides diagnosis (`is_watertight`, `is_winding_consistent`, degenerate/disconnected-component detection) both before and after -- `pymeshfix` can print a "MeshFix could not fix everything" warning even on a fully successful repair (confirmed empirically, not gated by its own `verbose` flag), so success is verified independently via `trimesh`, never trusted from `pymeshfix`'s own output. Repair runs early in Analysis & Solve, right after the Blender-exported STL is received and before gmsh ever sees it -- gmsh's STL-remeshing workflow assumes valid input topology, and invalid topology (holes, non-manifold edges, degenerate/duplicate faces, disconnected debris) produces confusing, hard-to-diagnose "gmsh artifacts" that are actually symptoms of unrepaired upstream geometry, not a gmsh bug. Blender's own "Make Manifold" (3D Print Toolbox) is a reasonable modeling habit but not relied on by the pipeline -- it's a manual step with no downstream verification, and is documented as best-effort/can fail on complex topology.
- Verify CalculiX card syntax against the 2.22 manual before generating; do not write cards from memory.

## Architecture rules

1. **Engine/UI boundary.** The engine (assembly model, mesh repair, gmsh meshing, `.inp` generation, solve, result parsing, verifiers) is a pure Python package with **zero `bpy` imports**, developed and tested with pytest outside Blender. The Blender layer is thin: collect scene → write files → launch engine subprocess → poll via `bpy.app.timers` → import results. Reversing this later is expensive. Guard it.
2. **Intermediate assembly model.** Blender scene → solver-agnostic assembly description → `.inp`. Never generate cards straight from Blender objects. The description holds:
   - **Bodies**: mesh ref, role, material (isotropic, or orthotropic + axis orientation). The rim **lining** is a body like any other (role `Body / Lining`), not a face selection — see "Rim lining" below.
   - **Bonds**: body pairs + interface type. Where adhesive quality must itself be an experimental variable (soundboard-to-lining, and any other glued joint), model the glue as a thin interposed body (its own mesh, thickness, and adhesive material: aliphatic resin, hide glue, etc.), `*TIE`'d rigidly to both adherents — the layer's own flexibility is the bond-stiffness knob, not an ad hoc parameter on the tie itself.
   - **Rim lining**: a Body-role object bonded to the soundboard at the real glue-strip footprint (~6-11 mm). Its own material/geometry governs how much it flexes under load. Whichever of its surface nodes are **not** part of a declared bond get an automatic **terminal condition** (object-level property, no face/node picking): `Fixed` (rigid bench/vice anchor, default), `Free` (unconstrained, floating-mass/string-suspended analogy — produces rigid-body modes like the free-free bare-plate stage; filter the same way), or `Spring` (grounded springs at the unbonded nodes with a stiffness value, approximating partial support). This is forward-compatible with V2+ back/side/air-cavity bodies: once something else is bonded to the lining's outer face, those nodes simply stop being "unbonded" and the terminal condition no longer applies there — no rework needed.
   - **Point attachments**: named locations (bridge feet / compensator points) + grounded spring K and/or applied force
   - **Analysis sequence**: optional static preload step, then eigenmode extraction. Build it expecting more than one analysis type later.
3. **Typed roles are first-class**: soundboard, rib/stiffener, bridge plate, body/lining, force/spring point, mass load. Roles drive defaults, verifiers and operator names. Name operators after guitar concepts ("Place Bridge Feet", "Apply String Preload"), not generic FEA steps. Role assignment (including the lining's terminal condition) must be checkbox/dropdown-easy, no manual face/node picking.
4. **Soundboard is a full 3D solid**, not a shell with thickness. Tapered, CNC-contoured and rib-less relief designs must work without re-architecture. Ribs, bridge plate, lining etc. are separate bodies by default.
5. **Boundary conditions are per-analysis configuration, never a pipeline default.** Free-free is only correct for bare-plate validation runs matching the free-suspended tap rig. The instrument model terminates at the rim lining body (see above), whose terminal condition and own material/geometry together determine how much energy the rim leaks — not a single scalar stiffness.

## Material library (Blender interface, decided)

Physical material records are carried by native **`bpy.types.Material` ID-blocks**, not a custom add-on-side list. An object's material slot *is* its physical material assignment — the same mechanism a user already knows from shading, repurposed so the slot holds lab-measured physical data instead of (or alongside) shader data. This buys link/append across a personal `materials_library.blend`, Asset Browser cataloguing/preview/drag-drop, and Blender's existing new/duplicate/make-single-user/fake-user/rename chrome, all for free — none of that gets rebuilt.

- **Isotropic and orthotropic are distinct material kinds** (not one type with a switch). Each kind has its own property set (isotropic: E, ν, density; orthotropic: the full stiffness constant set, density) and its own UI fields; don't force a shared schema that leaves fields meaningless depending on a toggle.
- **Grain/axis orientation is per-object, never per-material.** The same spruce material definition gets reused across boards with different grain directions, so orientation (X = radial, Y = longitudinal/grain, Z = tangential) is an object-level property, independent of which Material ID-block is assigned.
- **UI surface**: material picker (new/browse/X, same pattern as a normal material slot) plus inline physical fields, in the N-panel's **Material & Grain Orientation** sub-panel -- grouped with grain orientation (not Bodies & Roles), per the user's own UI preference: role assignment is a separate concern from material/orientation assignment, even though both are "per-object" settings. Mirrored into the Properties Editor's Material tab for deeper editing.
- Keep the engine/UI boundary rule intact: the engine's assembly model still receives plain material data (kind, constants, orientation) extracted from the `Material` ID-block and object, never a `bpy.types.Material` reference itself.
- **Built, not just decided (this session)**: `SoundboardLabMaterialSettings` (`addon/soundboard_lab/__init__.py`) now carries the full field set for both kinds -- orthotropic (`density`, `e_longitudinal`, `e_radial`, `e_tangential`, `g_lr`, `g_lt`, `g_rt`, `nu_lr`, `nu_lt`, `nu_rt`) and isotropic (`iso_e`, `iso_nu`; `density` is a single field shared by both kinds, same physical meaning regardless of kind). UI units are MPa (stiffness) and kg/m^3 (density) for readability; `extract_material()` does the kg/m^3 -> t/mm^3 conversion (factor 1e-12) when building the plain dict passed to the engine. Defaults are prefilled with `SPRUCE_PLACEHOLDER`'s own constants (orthotropic fields) and a generic `ISOTROPIC_PLACEHOLDER`-equivalent (`iso_e`/`iso_nu`) -- editable starting points, not meaningless zeros. `_draw_material_fields()` is shared by both UI surfaces (N-panel and Material tab) so they can't drift out of sync. The engine side gained a matching `IsotropicMaterial` dataclass, a `Material` union type, `validate_material()`/`material_to_dict()`/`material_from_dict()` dispatchers, and `write_shell_frequency_inp()` now writes either an orthotropic (`*ELASTIC, TYPE=ENGINEERING CONSTANTS` + `*ORIENTATION`) or isotropic (`*ELASTIC, TYPE=ISO`, no orientation -- stiffness is directionally invariant) card depending on which kind it's given. The CLI's `--material-json`/`--orientation` flags carry the resolved material dict and the resolved `*ORIENTATION` six-vector from the addon to the engine subprocess; both default to `SPRUCE_PLACEHOLDER`/identity if omitted (backward compatible with every existing caller/test). Verified empirically, not just "didn't crash": a deliberately much softer isotropic material gives frequencies substantially below the default spruce material's own, mode-for-mode, on the same real fixture (`tests/test_cli.py::test_cli_shell_path_custom_material_json_actually_used`); a 90-degree-rotated grain orientation gives different frequencies than identity on the same orthotropic material + fixture (`test_cli_shell_path_custom_orientation_changes_result`) -- proof the override actually reaches CalculiX, not silently ignored.
- **Starter library file**: `library/materials_library.blend` (generated by `library/build_materials_library.py`, see `library/README.md`) -- two named Materials (Spruce, a generic isotropic bridge-plate placeholder) with real Soundboard Lab fields set, demonstrating the actual Append/Link/Asset-Browser reuse mechanism this whole design buys "for free". Not part of the installed extension; a standalone convenience asset, regenerate the script if starter defaults change.
- **Persistence**: within a project, trivial and automatic -- any Scene/Object/Material property (including all of the above) is serialized into the `.blend` file on save, same as any other Blender data; nothing extra was built for this. Across *different* projects, the mechanism is the materials_library.blend file above (Append/Link), not a custom cross-project settings store -- a deliberate choice per this section's own "native ID-block" decision, not an oversight.

## Grain orientation (Blender interface, decided)

Prototyped and validated interactively (see session history); the design below is what shipped, not aspirational.

- **Storage**: `grain_rotation`, a per-object `FloatVectorProperty(subtype='EULER', size=3)` on the object's Soundboard Lab settings — same shape as Blender's own `rotation_euler`, so the N-panel shows familiar X/Y/Z degree fields. Independent of the Material ID-block (per the Material library section above).
- **Wired into the solve, not just the UI (this session)**: `analysis.py`'s `_compute_grain_orientation(obj)` resolves `grain_rotation` (relative to the object's own LOCAL axes) into the six raw `*ORIENTATION` numbers CalculiX's card needs, in WORLD space (consistent with `export_triangulated_stl`'s own world-space convention) -- `grain_rotation.to_matrix()` applied to the local radial/longitudinal basis vectors, then the object's own `matrix_world` rotation (via `to_quaternion()`, ignoring scale/shear -- an axis direction has no meaningful "scale") applied on top. `SOUNDBOARD_OT_analyze` passes the result to `start_solve` -> the CLI's `--orientation` flag. Verified with a real 90-degree object rotation giving the exact expected swapped world-space vectors, not just "didn't crash" (`scripts/addon_smoke_test.py`), and with a real CalculiX solve showing different frequencies for rotated vs. identity orientation (`tests/test_cli.py`).
- **Interactive rosette**: a `GizmoGroup` drawing three color-coded `GIZMO_GT_dial_3d` rings (red=X/radial, green=Y/longitudinal/grain, blue=Z/tangential), nested at different radii like a gimbal/armillary sphere rather than coincident circles — a thin flat soundboard otherwise puts the Z/tangential ring's plane flush with the board's own face, making it unreadable and hard to grab. Gated on role (Soundboard, Rib) **and** the assigned material being the Orthotropic kind; no rosette for isotropic bodies.
- **`target_set_handler`, not `target_set_prop` with `index=`**: `GIZMO_GT_dial_3d`'s `offset` target is declared as a plain scalar in Blender's own gizmo library, so `index=` is only valid as 0 (confirmed via a live `RuntimeError: index 1 must be below 1`) — it cannot bind one ring per Euler component the way the built-in Move gizmo's arrows bind to `location[i]`. Use explicit `get`/`set` callbacks per axis instead, closing over the axis index via a factory function (avoids the classic Python loop-closure bug).
- **`draw_options = {'ANGLE_VALUE'}`** is required on each dial or it draws a bare ring with no handle/indicator line at all — not optional polish.
- **`GizmoGroup` registration must be guarded** with `if not bpy.app.background:` (mirrors the existing keymap guard in this file). GizmoGroups need a window manager; headless/`--background` runs (smoke tests, CI) have none, and registering anyway leaves the class in a state where `unregister_class` later raises "missing bl_rna".
- **Custom `set` callbacks must never raise.** They run inside a gizmo modal callback on every mouse-move, in a more restricted context than a normal operator; an uncaught exception there makes Blender treat the whole drag as failed and revert the value to what it was at drag-start. Anything non-essential a callback does (e.g. forcing a UI redraw, since `target_set_handler` bypasses the automatic redraw-tagging that `target_set_prop`'s native RNA path gets for free) must be wrapped so it can't propagate.
- **The relative "grab anywhere, drag out a delta" interaction** (not "ring snaps to point at my cursor") is Blender's native rotate-dial convention, not a bug — matches the same mental model as the built-in Object Rotate (R) tool.
- Quick-align operators: `Align Grain to World Axes` (reset to local axes) and `Align Grain to Active Edge` (snap the grain/Y axis to a selected mesh edge, for matching a visible grain line), both in the same N-panel sub-panel as the Euler fields.

## Meshing and numerics (known traps)

- Use **quadratic tets (C3D10)**. Linear tets lock in thin bending and give eigenfrequencies that are systematically too high.
- **Cross-validated against FreeCAD FEM, isotropic case (session)**: same isotropic material (E=13800 MPa, density=460 kg/m^3, nu=0.45), same geometry, same fixed-edge boundary condition -- Soundboard Lab's modes 1-4 (155.6/286.7/331.4/487.4 Hz) came in consistently ~2-3.4% BELOW FreeCAD's own FEM result for the same four modes (161/294/342/498 Hz, frequencies taken directly from the user's own eigenmode-image filenames). Re-running with explicitly matched material settings reproduced the same gap, ruling out a material-input mismatch as the cause. The frequency RATIO (ours/FreeCAD) isn't perfectly flat across modes (0.9665-0.9789, ~1.2 percentage-point spread) -- a pure E/density difference would be an exact scalar multiplier on the whole eigenvalue problem and couldn't produce that spread, so some of the gap is mode-shape-dependent, consistent with a genuine formulation difference rather than only an input difference. Leading explanation: FreeCAD's FEM mesh very likely didn't have comparable quality/resolution through the ~2mm thickness (the exact failure mode this bullet point already warns about), making it artificially stiffer -- Soundboard Lab's result is trusted as the more physically correct one, not the FreeCAD result. Direction is also consistent with the independently-confirmed finding (same session) that shear modulus has a dominant effect on this geometry's frequencies -- a thin-shell-theory model that doesn't fully capture transverse shear would read stiffer/higher than this engine's real 3D C3D15 solid-element model, same direction as observed.
- Enforce **>= 2-3 element layers through thickness** (soundboard is ~2 mm). Use a thickness-aware gmsh size field, not one global size. Tapered thickness is its own explicit pass/fail test.
- Orthotropic stiffness must be positive definite; validate the constants before solving (small minor Poisson ratios have caused negative eigenfrequencies in her earlier work). Axis convention: **X = radial, Y = longitudinal/grain, Z = tangential**. Material constants come from her lab-measured library, never hardcoded defaults.
- Point-attachment locations must survive remeshing as identifiable nodes. Register them in gmsh as embedded/constrained points and carry node IDs into the spring/force cards. For Evergreen, these coincide with the Bridge Plate's boss extensions (registered CF-composite features, not arbitrary flat-plate locations) -- an easier case to keep robust through remeshing than an unmarked point.
- **Uniform 3D Delaunay tetrahedralization cannot economically resolve thin/flat objects** (a soundboard is the extreme case: ~300x400x2mm). Getting the required 2-3 layers through a 2mm thickness needs ~1mm elements; applied uniformly across the whole in-plane area that's ~1.36M elements for a single plate -- measured, not estimated. A scalar Distance+Threshold "refine near surface" sizing field does NOT fix this for a uniformly-thin plate, since every point is already close to a thin face everywhere. The fix needs anisotropic sizing: decouple in-plane element economy from through-thickness layer count entirely, via extrusion between explicit bottom/top reference surfaces (`src/soundboard_lab/shell_mesh.py`) producing C3D15 (15-node quadratic wedge/prism) elements instead of tets. Verified: 780 elements vs. 1.36M for the same 300x400x2mm plate at 3 layers, same qualitative eigenvalue shape. Element node order verified against CalculiX's own official example (`calculix/examples/elements/C3D15.inp`), not assumed.
- **Soundboard-role objects should use the shell/extrusion mesher, not the generic tet mesher** once a thin/flat footprint is known in advance -- this is a modeling-time fact (the user draws a 2D outline then thickens it, see the Soundboard Builder idea below), not something that needs to be rediscovered heuristically from an arbitrary 3D mesh.
- **Boundary conditions: free-free vs. fixed-edge, decided.** `write_shell_frequency_inp(..., fixed_edge=True)` clamps every node (translational DOFs 1,2,3 -- solid elements have no rotational DOFs) on the shell's outer perimeter, across every extrusion layer. The outer perimeter is found deterministically from the shell's own 2D triangulation topology (edges used by exactly one triangle = a boundary edge), not a heuristic guess at "flatness" from an arbitrary mesh. **Exposed as a Scene-level project setting (this session)**, along with number-of-modes and through-thickness-layer-count -- see "Global solution parameters" below; no longer hardcoded in `start_solve`.
- **Soundhole trap, caught and fixed**: the one-triangle-per-edge rule finds EVERY boundary loop in the topology -- the true outer perimeter AND any interior hole (a soundhole) are topologically indistinguishable by that rule alone. Fix: group boundary edges into connected loops (`find_boundary_loops`), then the loop enclosing the largest area (shoelace formula) is the true outer perimeter (`classify_boundary_loops`) -- any interior hole's loop is necessarily smaller, since the outer loop's enclosed region is a strict superset of the hole's footprint plus the material around it. Verified against a synthetic plate-with-hole test case (`tests/test_shell_mesh.py`) and a real CCX solve: free-free gives 6 exact-zero rigid-body modes then a 23.4 Hz fundamental; the same plate fixed-edge gives zero rigid-body modes and a 73.1 Hz fundamental (clamped = stiffer = higher frequency, as expected) -- confirms the constraint is doing something physically real, not just running clean.
- **Historical note (now stale, kept for context): "Not yet wired into the main Analysis & Solve pipeline."** This was true early in the session; the shell path has since been wired in as the live round-trip's default (role=Soundboard objects use `shell_mesh.py`, see "Full round-trip wired and verified" below). `write_frequency_inp_orthotropic` (the generic tet path's writer, still used for Rib/Bridge-Plate-role bodies in the bonding-exercise work) is also no longer orthotropic-only despite its name -- see the next bullet.
- **Tet-path material plumbing gap, found live and fixed (multi-body bonding exercise)**: `run_analysis()` (the generic tet path, `cli.py`) hardcoded `material = SPRUCE_PLACEHOLDER` internally and never even accepted a material parameter -- confirmed empirically, not just suspected: a real isotropic CF-composite material JSON was passed via `--material-json` while testing a real bridge-plate body, but the result's `material_name` still came back `"SprucePlaceholder"`. `write_frequency_inp_orthotropic` (mesh.py) also only handled `OrthotropicWoodMaterial`, same orthotropic-only gap `write_shell_frequency_inp` had before this session's material-library work. Fixed with the identical kind-dispatch pattern as the shell path: `write_frequency_inp_orthotropic` (name kept for backward compatibility with existing callers) now writes either `*ELASTIC, TYPE=ENGINEERING CONSTANTS` + `*ORIENTATION` (orthotropic) or `*ELASTIC, TYPE=ISO`, no orientation (isotropic); `run_analysis` takes `material`/`orientation` parameters (defaulting to the old hardcoded values, so every existing caller/test is unaffected); `main()`'s dispatch now passes the resolved material/orientation to both the tet and shell paths, not just the shell path. Verified on real geometry from the bonding exercise: a tapered spruce rib (`rib1.stl`, 300mm) solved cleanly with the real orthotropic material + a 90-degree grain rotation (free-free fundamental 104.9 Hz); the bridge plate (`bridge_plate2.stl`, 120x41x2.5mm) solved with the real forged-CF-composite isotropic material (E=32850 MPa, density=1300 kg/m^3, nu=0.3, no stated value so 0.3 used as the standard quasi-isotropic-composite default) and came back with `material_name` correctly showing the real material, frequencies landing in the 0.9-3.4 kHz range as physically expected for a compact, very stiff body (vs. the ribs' 74-120 Hz range for long, much softer spruce). New regression test (`tests/test_cli.py::test_cli_tet_path_custom_material_json_actually_used`) locks this in the same way the shell path's own equivalent test does.
- Note worth preserving (pre-existing, separate infrastructure, NOT touched by the above): `mesh.py` also has its own, older, narrower `IsotropicMaterial` dataclass (`name`/`youngs_modulus`/`poissons_ratio`/`density` fields) and `write_frequency_inp` function, used only by the Stage 2 validation-ladder test (`mesh_box` + a programmatically-generated box) -- a different, earlier, simpler piece of infrastructure than the real material-library's `materials.IsotropicMaterial` (`name`/`density`/`e`/`nu`) used everywhere else. Both classes happen to share the bare name `IsotropicMaterial`; `mesh.py` imports the newer one under the alias `GenericIsotropicMaterial` to avoid the collision, deliberately, not accidentally.
- **Real Blender-exported geometry is messier than synthetic test fixtures, confirmed on a real file (`tests/data/real_soundboard_with_defects.stl`), not hypothetically.** A boolean soundhole cut followed by Blender's own n-gon fill reliably produced 3 distinct, real defects, each caught and fixed in `shell_from_closed_mesh`:
  1. **Corrupted cap triangulation**: the top/bottom surfaces came out fan-triangulated from a hub vertex (median triangle aspect ratio ~25-30 vs. a healthy mesh's ~1.5), reproduced identically whether exported via Blender's binary STL exporter or the addon's own `calc_loop_triangles`-based ASCII export -- it's baked into the mesh's stored face topology, not an export-method artifact. Fix: never trust the cap's own triangulation; recover the true outer-edge/soundhole curves from the SIDE WALL structure instead (clean by construction -- confirmed exactly 2 simple loops, no junction defects, on the same defective file), then re-triangulate the recovered footprint FRESH with gmsh.
  2. **Z cross-contamination**: the same botched fill left a reversed-winding duplicate of a sliver triangle, which normal-direction classification alone misreads as a "bottom" face even though it's physically sitting at the top surface's Z level -- contaminates the bottom/top vertex clouds used for thickness lookup, producing a handful of zero-thickness vertices. Fix (`_reject_wrong_level_faces`): also require a candidate face's vertices to be closer to its own group's median Z than to the other group's.
  3. **Inconsistent triangle winding from the gmsh re-triangulation step**: confirmed ALL (not a mix of) regenerated triangles came out clockwise when viewed from +Z, silently producing inverted/negative-Jacobian C3D15 elements on effectively every extruded element (ccx failed with repeated "nonpositive jacobian" errors that misleadingly looked like a single bad element until checked carefully). Fix: flip any triangle with negative signed area before building the `ShellMesh`.
  - A 4th issue was a red herring, not a geometry bug: the re-triangulated footprint initially came out ~5x more elements than `element_size` should produce, because gmsh reuses the ORIGINAL (densely Blender-sampled) curve points directly as mesh nodes rather than coarsening them -- a Line between 2 points already closer together than `element_size` is never coarsened, only ever subdivided further. Fix (first pass): resample the recovered rim down to `0.5 * element_size` spacing via simple distance-based pruning. **Superseded**: distance-based pruning has no concept of which points are geometrically significant, so it can round off or erase a real sharp feature just because its neighbors happen to be densely sampled -- a real risk, not hypothetical, for soundboard outlines that deliberately include sharp-cornered features (a neck-block intrusion modeled as a sharp poly cut, or a Venetian cutaway's sharp apex where two curves meet at a point), and a correctness risk (not just cosmetic) for the planned body/lining bonding system if a required contact feature gets erased from the boundary curve. Replaced with curvature-aware closed-loop **Douglas-Peucker** (`_douglas_peucker_closed_loop`, anchor-pair split since DP is normally defined on an open curve) at `epsilon = 0.5 * element_size`, followed by a small (`0.1 * epsilon`) minimum-spacing safety-net pass (`_enforce_min_spacing`) -- DP alone doesn't guarantee a minimum spacing between surviving points, so the safety net still guards against the original near-duplicate-kink bug. Verified against synthetic torture cases (both an inward notch and an outward spike, densely sampled on both sides -- `tests/test_shell_mesh.py`): the feature's defining apex survives exactly, with zero shape/area distortion, while plain collinear padding still collapses away as expected. **Confirmed on a real file too** (`tests/data/real_soundboard_with_neck_block_notch.stl`, an independently-exported object with a deliberately sharp-cornered neck-block intrusion): the notch's 4 true corners survive with genuine near-right-angle turns (~90-102 degrees, measured directly), clearly separated from the smooth body outline's gentle curvature peaks (<40 degrees everywhere else); a full free-free + fixed-edge solve on the notched boundary runs cleanly end-to-end.
- **Mesh convergence study, real geometry (`tests/data/real_soundboard_with_defects.stl`, ~380x490mm, ~100mm soundhole), free-free, 3 layers**: swept `element_size` from 25mm down to 5mm. Frequencies changed by <0.1% from 10mm to 5mm (5x more elements, 5x longer solve) -- no meaningful accuracy left to gain past ~10mm for a soundboard at this scale. **Recommended default: ~10mm** for a normal solve, ~15-20mm acceptable for a fast preview (both within ~1% of the fully-converged answer here). Not yet generalized into an actual default/preset in the addon UI. Re-measured after switching to Douglas-Peucker (DP coarsens smooth regions more aggressively than the prior method at the same nominal `element_size` -- 3715 vs. 6101 triangles at 10mm on this file): solved frequencies shifted by ~2% (expected, not a regression) and the convergence trend itself still holds (~1.3% change from 10mm to 5mm, re-checked).

## Mesh preview & validation (Blender interface, decided)

"Trust me, it passed validation" isn't good enough — the mesh and its QA checks must be genuinely visible, not just pass/fail text.

- **Granularity control hides gmsh's sizing-field vocabulary.** One simple control (e.g. target element size, or Fine/Medium/Coarse presets) that the engine turns into a thickness-aware sizing field automatically, silently guaranteeing the >=2-3-layers-through-thickness rule underneath — matches the project's "small fixed vocabulary of guitar concepts" philosophy; luthiers don't need to understand gmsh size fields.
- **Boundary-skin preview mesh**: extract the generated mesh's outer triangular faces and build an actual lightweight Blender mesh object from them (meshio -> bmesh), named distinctly (e.g. `<Body> Mesh Preview`) and explicitly excluded from the role/assembly/bond system so it can't be mistaken for a real body. Gives native orbit/zoom/wireframe toggling for free.
- **Mesh-quality heat map on that same preview mesh**, driven by gmsh's own per-element quality metrics (aspect ratio, Jacobian) via a Color Attribute, viewable with zero material setup using Solid shading's "Attribute" color mode. This is the same node-import + Color-Attribute machinery the mode-shape results viewer needs (see below) — building it here first, on a lower-stakes problem, exercises that pipeline before it has to carry eigenmode results.
- **Thickness-layers-achieved is a number, not a wireframe.** Showing every internal tet edge to visually verify the layer-count trap would be unreadable at real-model scale; the engine counts layers per thin region from element connectivity directly and reports it (pass/fail or a count) rather than asking the user to eyeball it in 3D.

## Bonding: must be bulletproof (the reason this project exists)

SimScale and FreeCAD FEM both failed her on multi-material bonding via **silent** tie failure. Design the failure out:

1. **Pre-mesh proximity/contact detection** with an explicit, user-visible tolerance, classifying each body pair as bonded / not touching / interpenetrating. Role-aware: a rib bond is a thin strip along the glue face, a bridge-plate bond is a flat area, a lining bond is the rim glue strip (~6-11 mm wide); flag geometry that doesn't match the role's expected contact.
2. **Tie-completeness check** after meshing: every declared bond must produce non-empty paired surfaces on both sides. Fail loudly before calling `ccx`.
3. **Post-solve sanity checks**: with the rim lining's terminal condition applied there should be no unexpected rigid-body modes (unless the terminal condition is deliberately `Free`); a near-zero mode concentrated in one body flags a probable tie failure.
4. Bond only via **facet/surface-based `*TIE`** (no node-matched bonding). Master/slave chosen by a stated rule (coarser/stiffer as master), not by accident.
5. **Visual verification in the viewport**: role colors per body; a "Verify Assembly" operator drawing green/yellow/red bond regions via a `gpu` draw handler (non-destructive); click-to-inspect showing gap, bodies and tolerance in the sidebar. Eigenmodes imported as shape keys so a floating part is visible by eye.

## Results viewer (Blender interface, decided)

- **UIList of modes in the Results & Verification N-panel sub-panel** (mode #, frequency); no dedicated workspace needed for v1 — the default Layout workspace's N-panel plus the 3D viewport is sufficient. A dedicated workspace (viewport + N-panel + maybe a Spreadsheet editor for raw per-node numbers) is plausible later polish, not a v1 requirement.
- **Selecting a row drives the view, live**: sets that mode's shape key to its deformed pose (others zeroed) and switches the active Color Attribute to that mode's heat map, no extra click.
- **No animation.** A static pose per selected mode is sufficient; nothing oscillates.
- **Heat map scalar field: signed displacement along the soundboard object's own local Z axis** (its authored through-thickness direction as modeled — not world Z, not the grain-rotation material frame's Z). Soundboard bending modes have negligible in-plane motion; local-Z out-of-plane displacement is what her Chladni photos are actually defined by (nodal lines = zero-crossings of transverse motion), so this is the scalar that makes a direct visual comparison possible.
- **Colored on the Soundboard-role body's surface specifically**, even when ribs/bridge plate/lining are part of the same solve — matches where Chladni powder actually sits in her physical tests; other bodies aren't colored.
- **Per-mode auto-normalized color range**, not a shared scale across modes. Eigenmode amplitudes are solver-arbitrary (only defined up to a scale factor), so a shared scale would be meaningless; per-mode normalization doesn't move the zero-crossing nodal lines, which is what the Chladni comparison actually needs. Cross-mode amplitude comparison, if ever wanted, would need a different, physically-grounded scale (e.g. normalized against modal mass) — not the default.
- **First working slice built and verified** (session history): CalculiX's `.frd` file (never parsed before this -- only `.dat`'s frequency summary table was) has per-node, per-mode displacement vectors, extracted by `solver.parse_frd_mode_displacements` (fixed-width ASCII columns, verified against a real multi-mode file, not assumed -- a negative value's sign occupies the space a positive value's leading space would otherwise use, so naive whitespace-splitting silently garbles the data). `shell_mesh.mode_shape_z_displacement` maps a mode's per-node dict back onto the shell's own vertex order via `ShellInpWriteResult.top_layer_node_ids`. `analysis.build_mode_shape_preview` (addon side) builds a real 3D mesh object -- world-space vertices at the shell's own top-surface positions, so it can be freely orbited/viewed from any angle, not a flat projection image -- with a per-vertex `FLOAT_COLOR` Color Attribute (5-point blue/cyan/green/yellow/red ramp) and switches any visible 3D viewport to Solid+Vertex-color shading, matching the "zero material setup" decision above. Verified end-to-end on real solves of a dimensionally-corrected neck-block-notch fixture (orthotropic spruce, fixed-edge): mode 1 (66.5 Hz) is the symmetric fundamental; mode 2 (113.2 Hz) is a lateral dipole (bending across the *soft* radial axis); mode 3 (158.8 Hz) is a longitudinal dipole (bending along the *stiff* grain axis) -- the lateral-before-longitudinal ordering, reversed from an isotropic material's usual sequence, is a real, physically-expected consequence of the orthotropic stiffness ratio, not a coincidence.
- **Color normalization is symmetric around zero, not plain min/max.** An eigenmode's absolute sign/scale is mathematically arbitrary, so a mode can easily come back almost entirely one-signed (confirmed on a real solve: one mode's values ranged -244.6 to +0.18, nearly all negative). Plain `(dz-min)/(max-min)` normalization would then put a CLAMPED BOUNDARY's zero displacement near one extreme of the color ramp instead of the visual middle, making a zero-displacement edge look "hot" rather than neutral. Fix: normalize against `bound = max(|min|, |max|)` so zero always lands at the same green midpoint regardless of which way a given mode happens to be signed.
- **Full round-trip wired and verified, v1 slice**: pressing "GO!" in the Analysis & Solve panel (`SOUNDBOARD_OT_analyze`) now runs the shell/extrusion path end-to-end, not the generic tet path -- `cli.py`'s `run_shell_analysis()` chains repair → `shell_from_closed_mesh` → `write_shell_frequency_inp(fixed_edge=True)` → ccx → parse frequencies + per-mode displacements, and returns the solved mesh footprint and every mode's Z-displacement array in `result.json` (not just frequencies, unlike the tet path). Selecting a mode in the Results UIList (`SOUNDBOARD_UL_mode_results`, bound to `scene.soundboard_lab_selected_mode_index`) rebuilds a single "Soundboard Mode Shape Preview" object live via its own `update` callback -- a SEPARATE object from the user's authored soundboard mesh, not a recolor of the original (the solved mesh is a different topology entirely, from gmsh re-triangulation; coloring the original object would need new nearest-neighbor/barycentric interpolation, deliberately deferred, not built). Progress is a named-step checklist (`cli.py`'s `StepTracker`: Repair/Mesh/Write input/Solve/Parse results, each pending→running→done or error with a message), not a numeric percentage -- ccx itself is an opaque subprocess call with no fine-grained progress available, so a real progress bar would just be fake. Confirmed working live in a real GUI session on a real neck-block-notch soundboard (3827 triangles, modes matching engine-side testing exactly). **Material, grain orientation, and the three global solution parameters below were hardcoded through this point in the session -- no longer, see "Material library"/"Grain orientation"/"Global solution parameters".**
- **Z-fighting bug, caught live in the GUI and fixed (two-stage fix)**: the preview mesh's vertices sit at `top_z` -- the EXACT same world-space Z as the original soundboard object's own top surface -- so the two coplanar surfaces flickered against each other (the original's solid-fill shading vs. the preview's vertex-color shading). First attempt: `build_mode_shape_preview(..., surface_offset=0.5)` nudges the preview mesh slightly above the real surface. Confirmed INSUFFICIENT on its own, also live in the GUI: clean up close, but the same clashing/striping reappeared once zoomed out further -- depth-buffer precision degrades with distance from the camera, so a fixed small offset only pushes the problem out to a larger zoom level, it can't eliminate it. Real fix: `_set_soundboard_visibility()` hides the real soundboard object outright whenever its mode-shape preview is showing (no two coincident solid surfaces on screen at once, independent of zoom), and `start_solve()` restores its visibility as soon as a new solve is launched (whether or not that solve succeeds, so a stale preview never leaves the real object hidden with no explanation). `surface_offset` is kept as a (now purely cosmetic, not load-bearing) small lift so the preview still reads as genuinely "on" the surface rather than floating.
- **Rim-simplification epsilon tightened to `0.25 * element_size`** (from `0.5 *`): boundary point density barely affects total element count, since it only controls near-boundary resolution, not the interior (still governed by `element_size` alone) -- verified: halving epsilon from 0.5x to 0.25x grew a real neck-block-notch fixture's mesh from 3478 to 3827 triangles (~10%), for a visibly smoother boundary. Cheap trade, worth taking.

## Global solution parameters (Blender interface, decided)

Project-level analysis settings -- describing the analysis itself, not any one body, so they live on the **Scene**, not an object or material. Built this session, replacing what used to be hardcoded literals in `start_solve`'s CLI invocation:

- **Number of modes** (`scene.soundboard_lab_n_frequencies`, default 10), **boundary condition** (`scene.soundboard_lab_boundary_condition`, Fixed Edge / Free / Body-Lining, default Fixed Edge -- see "Boundary & Bonds UI" below). Number of Modes is in the Analysis & Solve N-panel sub-panel, above the GO! button; Boundary Condition moved to its own "Boundary & Bonds" sub-panel (see below) -- role assignment/material assignment/boundary assignment are each a distinct concern, not bundled just because they're all per-object or per-scene. **Through-thickness layer count moved to per-object (session correction)**: initially built as a Scene-level global (`scene.soundboard_lab_num_layers`), but caught before any real multi-body testing started -- a single global layer count can't work once multiple independently-meshed bodies (soundboard, ribs, bridge plate) each have their own thickness and may each need a different layer count. Now `obj.soundboard_lab.mesh_num_layers` (default 3, min 2), alongside the already-per-object `mesh_element_size`/`mesh_thickness_hint`. Number of Modes stays genuinely scene-global -- it's a property of the whole assembly's eigenvalue solve, not any one body's mesh.
- **Persistence**: trivial and automatic within a project -- Scene properties are serialized into the `.blend` file on save like any other Blender data, no extra persistence code needed. A cross-project *default* (e.g. "always start a brand new project at num_layers=4") would need a different mechanism (e.g. Blender's own Save Startup File, or an add-on-preferences-level default) -- not built, not asked for yet.
- `SOUNDBOARD_OT_analyze` reads these three Scene properties (plus the per-object `mesh_element_size`/`mesh_thickness_hint`, extracted material, and resolved grain orientation) and passes them all to `start_solve`, which forwards them to the CLI's `--n-frequencies`/`--boundary-condition`/`--num-layers`/`--material-json`/`--orientation` flags. `start_solve`'s own parameters still default to the old hardcoded values (10/fixed_edge/3/None/None) so every existing direct caller (tests, the smoke test) is unaffected by the signature change.

- **Boundary Condition dropdown moved here** from Analysis & Solve, and extended with a third option: **Body/Lining** -- defers to the Body/Lining-role object's own per-object `terminal_condition` (Fixed/Free/Spring, already built) instead of a single scene-wide rule. This is literally the already-decided "Rim lining" architecture (Architecture rule #2) made solve-selectable, not a new concept.
- **Wired to the solve (rim lining, built and verified -- see "Rim lining solve" below).** Selecting Body/Lining raises a clear `SoundboardLabSceneError` (inline in the panel and at solve time) only when no Body/Lining-role object exists, or more than one does. `analysis.check_body_lining_boundary_condition()` is the single source of truth for this check, deliberately independent of `get_preferences()` (same testability rationale as `start_solve`) so it's exercised directly in the headless smoke test.
- **Multi-object bonding design (confirmed with the user, not yet built)**:
  - **Scope: role-scoped to the Soundboard only for V1.** Every non-Soundboard body (Rib, Bridge Plate, eventually Lining) bonds to the Soundboard; no general N:M any-pair contact mapping. Explicitly accepted simplification even for cases like a rib passing over the bridge plate -- the "transitive" stiffness coupling through the shared Soundboard body is expected to be a close enough approximation for V1.
  - **Detection, built and verified this session (`src/soundboard_lab/bonding.py`)**: `find_contact_footprint()` -- for every point in a body's point array, find the nearest point on the Soundboard's surface (`trimesh.proximity.closest_point`, an exact nearest-point-on-triangle query) and classify it as "in contact" if within `tolerance` (the user-controllable epsilon, default 0.1mm, chosen as "easy to see when modeling"). Needs the `rtree` package (added as an explicit dependency -- `trimesh.proximity.closest_point` lazily imports it for its spatial index and raises a bare `ModuleNotFoundError` if missing, caught empirically, not assumed). **Real finding: a body's raw design-time STL vertices are far too sparse to use directly** -- a plain box-topology rib (e.g. a real tapered rib, modeled from a cube) has only 8 total vertices, so a coarse check can only ever "see" contact at the few corners that happen to exist, nothing along the middle of a long touching edge (confirmed: only 2 soundboard faces registered as touched for a 300mm rib using raw STL vertices). The real, accurate check (`find_contact_footprint_from_meshed_body`) must run on the MESHED (post-gmsh) node positions instead, which are dense across the whole surface -- confirmed empirically: 16 soundboard faces touched (8x more) on the identical real geometry once meshed. `find_contact_footprint_from_files` (raw STL) is kept as a fast, honestly-documented "coarse/design-time preview only" convenience, not something a real bond decision should be based on. A future-Detect-button UI (not yet built -- see below) will need to actually mesh each non-Soundboard body first, not just read its STL vertices.
  - **Explicit, reviewable bond list** -- detection populates a list (bonded/not, per non-Soundboard object relative to the Soundboard), not silently baked into solve, matching the established step-checklist/verify-don't-assume culture.
  - **Visualization**: color each body's detected-bonded footprint vs. unbonded regions -- specifically to make incomplete/jagged bonding AT EDGES visually obvious, not just a binary yes/no. See "Generated collections & bonding proxies" below for how.
  - **Solver-mesh-based detection pipeline, built and verified (`bonding.detect_bonds`)**: meshes the Soundboard exactly as the solver does (`shell_from_closed_mesh`, including its perimeter simplification) and closes it into a watertight reference surface (`shell_surface`); meshes every other body with the tet mesher and takes its outward-wound outer skin (`tet_boundary_skin`); classifies each body (`classify_bond`) as `contact` (candidate bond, for review -- never auto-accepted), `not_touching` (with the nearest gap reported), `interpenetrating`, or `geometry_error` (repair/mesh failure, reported per body without aborting the rest). Detection runs against the **meshed** Soundboard, never the authored STL or the mode-shape display: a bond decided against geometry the solver never sees could silently disagree with the real tie. Contact is reported as an **area** (skin triangles with all corners within tolerance), not a vertex fraction, so it's comparable to the intended glue footprint and independent of mesh density -- verified: rib1's contact area is 1800.0 mm², exactly its real 300 x 6 mm footprint. Interpenetration is checked **both ways**: body skin nodes inside the Soundboard, AND Soundboard surface vertices inside the body -- the second catches a thin Soundboard edge poking into a body between the body's own skin nodes, which the first alone misses (synthetic test proves the case). Signed distances use trimesh's convention: positive = inside.

The user fixed and re-exported it from Blender; the CLI now adds a "self-intersection -- Merge by Distance" hint to that gmsh error.

They're tagged as add-on-owned and linked back to their source object, never become assembly/solve inputs, and a refresh replaces only these tagged objects -- never touches authored content. Authored objects are never moved or modified.

The mode-shape preview's old 0.5 `surface_offset` is removed; it now lives in `Analysis Results` as a tagged `MODE_SHAPE` object sitting exactly on the solved top surface (coplanar Z-fighting with the authored Soundboard is still handled by hiding that object while the preview shows). The bond overlay draws with depth testing off, so coplanar/sandwiched contact never Z-fights.

Objects are tagged via `obj.soundboard_lab.generated_kind` (`BOND_PROXY` / `SOUNDBOARD_PROXY` / `MODE_SHAPE`) plus `source_object`; `analysis.find_role_objects` excludes them even if a user assigns a role. Refresh (`generated.remove_generated_objects`) deletes only tagged objects (and their now-unused meshes) -- user objects dropped into the collections survive (smoke-tested). Proxies are at identity transform with world-space vertices, `display_type='WIRE'`, `hide_render`. Body proxies store `BondDistance` (float) and `BondStatus` (RGBA) point attributes so the overlay survives a reload. Moving a source back restores "current". A stale Soundboard reference makes every result stale. Stale proxies draw dimmed. Confirmed: the handler fires even in `--background` on `view_layer.update()`.
  - **Tie strength: rigid `*TIE` for V1** (matches the already-decided bonds architecture). A scalar glue-flexibility knob is a planned later refinement; the original architecture's full separate-thin-glue-body-with-its-own-material model is a further-out refinement beyond that, not needed for the first exercise.
  - **Master/slave: hardcoded Soundboard=master for every tie in V1** (per the CalculiX manual: slave can be node- or face-based, master must be element-face-based -- see "`*TIE` mechanics proof" below). No per-object override UI built -- a per-object boolean would be the natural mechanism if ever needed (sufficient for V1's always-two-body-per-tie scope; a full numeric-priority hierarchy would only earn its complexity once bonding goes general N:M, not yet in scope), but general FEA "stiffer body = master" guidance is mostly folklore from static/stress analysis where local stress concentration matters; for pure eigenfrequency/modal analysis the sensitivity is expected to be much smaller. Revisit only if a real case empirically demonstrates master/slave choice meaningfully changes eigenfrequencies (same empirical-swap-and-compare style as the `*TIE` proof below), not before.

Ribs (long thin battens) very plausibly hit the same "thin/flat objects need anisotropic sizing" trap that drove the Soundboard's whole shell/extrusion mesher -- not assumed either way, needs checking against real rib geometry. The Bridge Plate is more block-like and likely fine with the simpler generic tet mesher (built, but never wired into the live round-trip).

A body with zero glue-face nodes is a `ValueError`, never a silently floating body. CLI: `--bodies-json` (shell path only, `{tolerance, bodies:[{name, stl, element_size, material, orientation}]}`); bodies are repaired + tet-meshed inside the existing "mesh" step, and the result carries `bonded_bodies: [{name, tie_nodes}]`. Proof: free-free Soundboard (element size 10) + rib1 (element size 2) gives exactly 6 near-zero modes (max 0.67 Hz) and mode 7 at 18.5 Hz; the same board alone has mode 2 at 23.4 Hz, tied 42.8 Hz across the rib. Add-on: GO! calls `bonds.gather_bonded_bodies` -- Rib/Bridge Plate bodies with missing or stale bond results block the solve ("run Detect Bonds first"/"out of date"); non-CONTACT bodies are left out with a WARNING; bonded bodies use their own Material (else engine spruce), grain orientation and `mesh_element_size`, tie tolerance = `soundboard_lab_bond_tolerance`. Under `body_lining` the board's own edge is left free; the lining's **outer wall** (where the sides glue -- user decision) is the terminal: `outer_wall_nodes` takes near-vertical skin faces whose outward normal points away from the nearest segment of the board's outline, minus the glue nodes. `fixed` = `*BOUNDARY` 1-3; `free` = nothing; `spring` = SPRING1 per direction, **stiffness is the total N/mm per direction, shared equally across terminal nodes** (must be > 0). The lining only joins the solve when the scene BC is Body/Lining (under Fixed Edge / Free it's ignored), and then it must be CONTACT. Real fixture (board 10 mm, lining 4 mm, Fixed): board + lining 73.7 / 126.0 / 174.1 Hz (vs bare fixed edge 66.5 -- the 10 mm glue strip is held); + 4 ribs + bridge plate 88.7 / 178.4 / 214.7 Hz; ~70-140 s solves. Free terminal gives 6 rigid modes (noise up to ~1.7 Hz with ties, so tests use relative thresholds).
  - **Meshing fixes found on the lining (apply to every body, `mesh.py` / `repair.py`)**: (a) `classifySurfaces(..., forceParametrizable=True)` -- without it the lining's long thin ring faces hung gmsh's 2D mesher forever (not a catchable error); (b) `Mesh.SecondOrderLinear=1` -- curved mid-side nodes inverted thin tets (ccx "nonpositive jacobian"); straight is correct for faceted STLs anyway; (c) `repair.flip_cap_triangles` -- Blender triangulates big flat n-gons into ~180° "cap" triangles (286 on the lining), and gmsh's "segment and facet intersect" PLC check then passes or fails on 1e-6 roundoff (the add-on's own re-export of the same lining failed where the file meshed). Coplanar edge flips remove them without moving a vertex; caps whose long edge is a crease are left alone. Reported as `RepairReport.cap_triangles_flipped`.
- **Point attachments & mass loads, built and verified (`assembly.PointAttachment`; CLI `--attachments-json`; `tests/test_attachments.py`; smoke test)**. The user chose simple abstract attachments over realistic compensator bodies; footprints and a compensator body bearing on the bridge plate would need a body-to-body attachment tree, which is deferred unless validation against the real instrument shows modelling error.
  - **What it is**: a Point Attachment or Mass Load role, usually on an **Empty**, acting at its world origin. `find_attachment_objects` accepts any object type; `find_role_objects` stays mesh-only, so attachments are never bodies.
  - **Placement**: the origin snaps to the nearest surface of the board (top or bottom face) or of any bonded body (rib, bridge plate, lining). A snap beyond 5 mm is an error.
  - **Patch**: the patch is the nodes within `attach_radius` on faces facing the same way as the contact face, so it never leaks through to the board's other face. A radius of 0, or no nodes in range, falls back to the single nearest node.
  - **Physics**: a grounded **Z-only** spring (ground = rigid back) plus a lumped mass (`*MASS`). Both are totals, shared equally across the patch nodes.
  - **UI units**: stiffness in **kgf/mm** (×9.80665 → N/mm in `gather_point_attachments`) and mass in **grams**. A Mass Load has mass only; the user models the **bridge as a Mass Load**.
  - **Result**: the result JSON reports `point_attachments` (body, nodes, snap distance), and the solve message shows them.
  - **Validation**: a free plate on a soft k = 0.01 N/mm spring gives 3.4954 Hz against √(k/M)/2π = 3.4981; adding a 20 g point mass gives 2.5006 Hz against 2.4947. Both are within 0.3%.
  - **CalculiX quirk**: a `*SPRING`/`*MASS` data line that looks like an integer ("1") is read as "card without data" and cascades into *STEP errors. All values are written in E-format (`_real`).
  - **Evergreen use**: put one Empty per compensator on the bottom of each bridge-plate boss (2.72 kgf/mm, 3 g), and put the bridge as a Mass Load with a patch radius covering its footprint.
  - **`*TIE` mechanics proof, done and verified (`tests/test_tie_mechanics.py`)**: before tackling real multi-body geometry, confirmed CalculiX's `*TIE` card (verified against the real CalculiX 2.22 manual's `*TIE`/`*SURFACE` semantics first, not assumed -- POSITION TOLERANCE is the max orthogonal slave-node-to-master-face gap, defaulting to 2.5% of typical element size if unspecified; ADJUST=NO means don't snap slave nodes onto the master face; master must be element-face-based, slave can be nodal or face-based; hex/tet/wedge face-numbering conventions confirmed directly from the manual, not guessed) actually reproduces a truly continuous structure's behavior in this project's own ccx invocation. Three hand-built two-hex `.inp` fixtures (same material/units as the existing `stage1_single_hex.inp` reference): a continuous shared-node reference, the same geometry split into two independently-numbered hexes joined by `*TIE`, and a disconnected negative control with no tie at all. Result: the tied case reproduces the continuous reference's elastic-mode frequencies to within 0.01% and the correct rigid-body mode count (6, not 12) -- proof the tie genuinely couples independently-meshed bodies the same way shared nodes would, not just "something that doesn't crash". The disconnected negative control shows exactly 12 near-zero rigid-body modes (6 per independent body), confirming the tie in the other case is doing real mechanical work, not a no-op that would have passed either way.

## Scope

**In (v1):** eigenmode analysis of soundboard + bridge plate + rib array; material library (orthotropic spruce proxy, isotropic bridge plate, rib composites) applied per body; rim lining body with its own material/geometry and a per-object terminal condition (fixed / free / spring); two point springs (compensators) at the bridge plate; optional static string-force preload run A/B against no-preload; mass loading; MAC comparison against measured mode shapes; mode-shape viewer.

**Evergreen-specific:** two compensator springs (~2.72 kgf/mm each, ~3 g), bolted to the bridge plate; plate stiffness is largely swamped by them, so they must be in the model. Goal is a **calibrated baseline model of the current instrument** that reproduces measured modal frequencies (M1/T1 about 178-182 Hz, A0 about 98-102 Hz), then use it to test bracing candidates toward M1 about 190-200 Hz.

**Out for now (deferred, keep the analysis-sequence model extensible):** mobility / driven damped response, full-box coupling (back, sides, air cavity), other solvers. The lining's terminal-condition rule (applies only to currently-unbonded nodes) is designed so adding these later doesn't require reworking the rim model.

**v1.5+ (deferred, confirmed viable):** **curved orthotropic material orientation**, for bent ribs where the grain (Y/longitudinal) axis should sweep along a curve's tangent rather than stay one fixed Euler rotation for the whole object -- analogous to the curve-sweep modeling technique already used for the geometry itself, and valuable for her common methods. Confirmed against the real CalculiX manual (not assumed): `*ORIENTATION` can reference a `*DISTRIBUTION` card giving a **different local axis per element/element set**, applied via `*SOLID SECTION ..., ORIENTATION=name` -- a genuinely supported mechanism, not exotic. Real engine work required (not just a UI picker): for each FE element, find the nearest point on the driving curve and take its tangent as that element's local Y axis, emitting one `*DISTRIBUTION` row per element. Likely reuses the same curve object already used to sweep the rib's geometry, rather than a separate spline tool. UI would need a per-object toggle alongside the existing constant-orientation rosette: Fixed (today's Euler + rosette) vs. Follow Curve (pick a curve object).

**Backlog -- wrap-up feature after the v1 essentials: result gallery export (viability workshopped with the user, not built).** One image sheet per solve so results from many projects can be collected side by side for reference.
- **Rendering: engine-side 2D plots (matplotlib, a new engine dependency), not Blender renders.** Each tile is a top-down view of the board outline coloured by vertical movement (signed, normalized per mode), with zero-movement lines drawn in black -- the numerical equivalent of the user's Chladni tests. Bonded-body outlines (ribs, plate, lining) are drawn faintly on top. Deterministic, fast, testable without Blender. Blender viewport renders (3D strip) are a possible later option, not the default.
- **Layout:** default 5 columns; rows = ceil(modes / columns); columns adjustable. Tile = mode number, frequency in Hz, the plot, and later stats.
- **Title block:** project / .blend name, timestamp, boundary condition (plus lining terminal and stiffness), Soundboard material and grain angle, number of layers, element sizes, bonded bodies with tie counts.
- **Output:** PNG plus PDF, plus a sidecar JSON with the same numbers for later cross-project comparison. Default folder next to the .blend; name `<project>_<timestamp>_modes.*`.
- **Prerequisites to check:** build the sheet from the results stored in the scene (solve work folders are temporary), and confirm the per-mode shape data saved there is enough to plot after reopening a .blend.
- **Hooks for later:** **"MM" = monopole mobility / admittance** (user's meaning -- net volume velocity per unit bridge force, Gore-style), destined for the JSON dump rather than the tiles. Viable from existing modal data: ccx normalizes eigenvectors to unit modal mass, so per mode the net volume displacement V_n = sum of top-surface w_n x node area and the bridge-point displacement phi_n(b) give a modal sum Y_V(w) = sum i*w*phi_n(b)*V_n / (w_n^2 - w^2 + i*eta*w_n^2); the static limit (w -> 0) is the stiffness-style volume-per-force figure. Needs a defined drive point (bridge saddle location, ties to the Evergreen force path) and a damping assumption eta -- it's the first step into the deferred "mobility / driven response" scope, so keep it per-mode (V_n, phi_n(b), monopole effective mass) plus the summed curve. Also later: MAC against measured shapes as tile annotations.

## Evergreen force path (patent-derived, see `docs/1431-02 - Drawings_r1.pdf`)

The soundboard is in a genuine **no-static-stress regime** by mechanical design, not by simplifying assumption:

- **Longitudinal string tension (~160 lbf x2)** is carried entirely by an internal tension member (a stainless-steel cable) running the full body length under the soundboard, anchored at a rigid Load Bearing Structure at the neck block on one end and at the Force Compensation Structure (anchored to the back) on the other. It never loads the soundboard.
- **The tailpiece is suspended above the soundboard** by string tension and the tension-member cable, not resting on it. The cable doubles around a low-friction bearing (a pulley) at the tail block, converting the string pull into an upward force on the Force Compensation Structure's springs (parabolic leaf springs, CF composite).
- **The bridge is the only point of contact** between this entire tensioning system and the soundboard. It floats (not glued), held down by a net residual transverse force (~36 lbf) that the compensator springs balance against string tension.
- **Round 1 consequence**: skip the `NLGEOM` static-preload -> frequency chain entirely for the Evergreen baseline case; a plain linear modal analysis is physically correct here, not an approximation. Reserve the `NLGEOM` preload chain for the deliberately-detuned "advanced case" (compensator K / preset height tuned so the full-tension equilibrium pose is +1 to 1.5 mm convex instead of neutral).
- **Bridge-to-soundboard interface**: model as bonded (not true floating contact). ~36 lbf of continuous clamping force is far larger than any expected dynamic separation force, so no lift-off/rocking in the small-amplitude eigenmode regime.
- **Point Attachment locations**: the two Bridge Plate boss extensions (CF composite) directly opposite the compensator feet. Bridge feet register against these bosses, not the spruce itself -- load bears on the boss. Apply both compensator mass (~3 g) and spring K there.
- **Maximum dynamic string forcing: +/- 1 lbf** (a deliberately generous outside estimate for aggressive strumming). Tiny relative to the ~36 lbf static clamping preload -- confirms no bridge-separation risk even dynamically, and is the relevant magnitude once driven/forced-response analysis (deferred, see Scope) is built.
